## 1. Repository architecture

### What exists today

```text
fps-study-hub/
├── index.html, app.js, styles.css      # legacy interactive app (unchanged, still live)
├── data/                                # canonical lesson content — source of truth
│   ├── course-map.js  block-a.js
│   ├── fps-course-map.js  fps-block1.js  fps-block2.js  fps-block3.js  fps-block4.js
│   └── glossary-extra.js
├── scripts/
│   ├── convert-to-markdown.js           # data/*.js -> docs-site/content/**/*.md
│   └── build-search-index.js            # docs-site/content/**/*.md -> assets/embeddings/index.json
├── docs-site/                           # new MkDocs Material documentation site
│   ├── mkdocs.yml
│   ├── requirements.txt
│   ├── .markdownlint.json
│   └── content/                         # docs_dir — mostly *generated*, see below
│       ├── index.md  fps/index.md  cpcm/index.md     # hand-written landing pages
│       ├── fps/f1.../  fps/f2.../  fps/f3.../  fps/f4.../   # generated lesson pages
│       ├── cpcm/block-a-foundations/                 # generated lesson pages
│       ├── glossary/index.md                         # generated
│       ├── interview-prep/  mock-exams/  case-studies/  resources/  # stub pages, hand-written
│       ├── assistant/index.md                        # Knowledge Assistant page, hand-written
│       └── assets/
│           ├── stylesheets/extra.css
│           ├── javascripts/assistant.js
│           └── embeddings/index.json    # generated retrieval index
└── .github/workflows/
    ├── docs-deploy.yml
    └── docs-validate.yml
```

### Why this shape, and the key decision: two content forms, one source of truth

The single highest-leverage architectural decision here is **`data/*.js` stays canonical; `docs-site/content/**/*.md` is a build artifact**, regenerated by `scripts/convert-to-markdown.js`. The alternative — hand-writing Markdown as the source of truth — was rejected because it would mean maintaining two parallel copies of every lesson (the JS object driving the interactive flashcards/quiz app, and a Markdown copy for the docs site) that inevitably drift. Generating one from the other means a lesson is written exactly once, in one place, and both surfaces render it consistently. `docs-validate.yml` enforces this: it regenerates the Markdown in CI and fails the build if the committed copy is out of sync, so nobody can hand-edit a generated file and have it silently diverge.

### Rationale for each top-level folder

- **`data/`** — canonical content. One `blockN.js` file per curriculum block, each exporting a `FPS_BLOCKn` / `BLOCK_X` object with a fixed lesson schema (see §2). This is what actually scales: adding lesson 22 is "add one object to an array," not "restructure a folder tree."
- **`scripts/`** — small, dependency-light Node scripts that transform `data/` into everything else (Markdown, the search index). No build framework, no bundler — these are two files under 200 lines each, intentionally.
- **`docs-site/content/`** — mirrors the *curriculum* structure (`fps/f1-.../`, `cpcm/block-a-.../`), not the source-file structure, because URLs and navigation should reflect how a learner thinks about the content, not how it's stored.
- **`interview-prep/`, `mock-exams/`, `case-studies/`, `resources/`** — created now as stub pages (§1 of the brief asked for these as first-class sections even before they have content) specifically so the nav structure, URL scheme, and search index don't need to change shape later — only content gets added into an already-correct slot.
- **`assets/embeddings/`** — deliberately named `embeddings` even though the current implementation is term-frequency retrieval, not vector embeddings (§5) — this is the slot where real embeddings will drop in later without a URL/path change.
- **`.github/workflows/`** — CI at the repo root is a GitHub convention (Actions only discovers workflows in `.github/workflows/`), so despite `docs-site/` being logically separate, the workflows have to live at the top level.

### How this scales from 25 lessons (today) to 1,000+

The pattern that has to hold at 1,000 lessons is: **adding a lesson never means touching routing, build config, or navigation code by hand.** Today, adding FPS lesson 22 means: add an object to `data/fps-block5.js`'s `lessons` array, add one line to `FPS_COURSE_MAP` — everything else (the interactive app's routing, the Markdown generation, the search index, the MkDocs nav for that block, the RAG corpus) picks it up automatically on the next build. At 1,000 lessons the only structural change needed is splitting `fps-course-map.js`-style registries by *domain* rather than one flat array (e.g. a `data/tracks/` directory with one manifest per track: `fps.js`, `cpcm/`, `cards.js`, `treasury.js` — see §7), so no single file becomes an unwieldy multi-thousand-line registry. The lesson-object schema itself does not need to change at any scale.

## 2. Markdown / lesson data template

Every lesson — whether authored as a `data/*.js` object (today) or, if the project ever moves to Markdown-first authoring, as frontmatter — follows the same fixed schema. This is what `convert-to-markdown.js` maps into Markdown sections.

### Canonical JS schema (current source of truth)

```js
{
  n: 21,                          // lesson number within its block
  title: "Fraud Investigation",
  tag: "essential",               // essential | supplementary | advanced
  objectives: "...",              // one paragraph, becomes the frontmatter summary
  explanation: "...",             // core concept teaching, 2-4 paragraphs
  keyTerms: [["Term", "Definition"], ...],
  example: "...",                 // one worked, original example
  diagram: { type: "flow", orientation: "vertical", steps: [...] },
  comparison: { caption: "...", headers: [...], rows: [[...], ...] },
  examTips: ["...", ...],
  memoryTrick: "...",
  keyPoints: ["...", ...],
  mcqs: [{ q: "...", options: [...], a: 1 }, ...],
  scenarios: [["question", "answer"], ...],
}
```

### Equivalent Markdown + frontmatter (generated output, for reference / for anyone contributing lessons Markdown-first later)

---

track: "FPS analyst deep-dive"
block: "Investigations"
tags: ["Investigations", "Fraud Investigation"]

This is a working example, not a mock-up — see `docs-site/content/fps/f4-investigations/21-fraud-investigation.md` in this repo, produced by `node scripts/convert-to-markdown.js`.

### Frontmatter field reference

| Field | Purpose | Used by |
|---|---|---|
| `title` | Page title, nav label | MkDocs, search |
| `lesson_number` | Ordering within block | nav generation |
| `track` | "FPS analyst deep-dive" / "CPCM curriculum" | breadcrumbs, filtering |
| `block` | Parent block title | breadcrumbs |
| `tags` | Free-text topic tags | `tags` MkDocs plugin, future tag browsing |
| `summary` | First ~180 chars of objectives | meta description, search result snippets |

## 3. Documentation site strategy

| | GitHub Pages (raw HTML) | MkDocs (plain) | **MkDocs Material** | Docusaurus |
|---|---|---|---|---|
| Search | None built-in — must hand-roll (this repo did, for the legacy app) | Basic Lunr search | **Excellent, prebuilt, instant, works offline** | Algolia (needs external account/index) or basic local search plugin |
| Setup cost | Low (already done) | Low | Low–medium | Medium–high (React/Node toolchain) |
| Content format | Hand-written HTML/JS | Markdown | Markdown | Markdown/MDX (supports embedded React components) |
| Theming/navigation | Fully custom, fully manual | Basic | **Tabs, sections, dark mode, versioning, admonitions, collapsible Q&A — all built in** | Fully custom, React-based, most flexible |
| Best fit | A small, highly interactive app (flashcards/quiz state machine) | Simple docs | **Content-heavy knowledge base at any scale, standard docs UX expected by readers** | Product docs needing custom interactive React widgets throughout |
| Deploy | GitHub Pages, branch-based | GitHub Pages via `mkdocs gh-deploy` or Actions | Same | GitHub Pages via Actions, or Vercel/Netlify |
| Team/learning curve | None (vanilla JS) | Very low (Python + YAML) | Very low | Higher (React, Node build pipeline) |

**Recommendation: MkDocs Material**, which is what's implemented in `docs-site/`. Reasoning specific to this project:

1. **Search is the whole point of this request**, and Material ships a genuinely fast, fuzzy, highlighting client-side search with zero extra work — `plugins: [search]` in `mkdocs.yml` is the entire configuration.
2. **The content is prose-and-diagram knowledge, not an interactive product** — Docusaurus's main advantage (arbitrary embedded React components) isn't needed for lesson pages; the one place custom JS *is* needed (the Knowledge Assistant, §5) works fine as a plain `<script>` tag via `extra_javascript`, which Material supports natively.
3. **Python + YAML is a lower ongoing maintenance burden** than a Node/React toolchain for a project that's fundamentally about content, not application engineering.
4. **The legacy interactive app doesn't need to be rebuilt** — it's kept exactly as-is at `/app/` in the combined Pages output (see below), so nothing already working is put at risk by this migration.

### Setup (already done — for reference)

```bash
pip install -r docs-site/requirements.txt   # mkdocs, mkdocs-material, mkdocs-awesome-pages-plugin
cd docs-site && mkdocs serve                # local dev server, live reload
mkdocs build --strict                       # production build, docs-site/site/
```

### Deployment workflow

`docs-deploy.yml` (already implemented, see §9) does, on every push to `master` that touches lesson data or the docs site:

1. Regenerate Markdown from `data/*.js`.
2. Rebuild the retrieval index.
3. `mkdocs build --strict`.
4. Copy the legacy interactive app into `publish/app/` alongside the docs build, so **both sites are served from one Pages deployment** — the docs site at the domain root, the original flashcard/quiz app at `/app/`.
5. Deploy via `actions/deploy-pages`.

**One manual step required from you**: in the repo's Settings → Pages, change the source from "Deploy from a branch" to **"GitHub Actions"**. This is a one-time setting change; the workflow can't do it for you via a normal push.

## 4. Search & knowledge discovery

Implemented today:

- **Global full-text search** — MkDocs Material's built-in `search` plugin, prebuilt index, instant client-side results with highlighting, no server. Also independently implemented for the *legacy* interactive app (`app.js` → `#/search`, sidebar box, `/` keyboard shortcut) so search works on both surfaces during the transition period.
- **Category navigation** — `nav:` tree in `mkdocs.yml`, grouped by track (FPS / CPCM) then block, matching how a learner actually studies (in sequence, within a track).
- **Tag system** — every generated page carries `tags: [block title, lesson title]` in frontmatter via the `tags` MkDocs plugin; this is a thin implementation today (tags are mostly block/lesson names) and is the clearest "cheap to extend" hook — richer tags (e.g. `iso20022`, `fraud`, `interview-question`) can be added to the lesson schema's `keyTerms`/`tags` field without any pipeline change.
- **Cross-linking** — every generated lesson page links back to its block index; block indexes list all lessons; the landing page links every track and block. What's *not* yet built: automatic "related lessons" links between, say, the CoP lesson (F2) and the fraud investigation lesson (F4) that both discuss it — see roadmap below.
- **Learning paths** — currently implicit (work through F1 → F4 in order, or A → H for CPCM). Not yet a first-class feature.

**Roadmap for this section**: a `related` frontmatter field (a list of lesson slugs), populated either by hand or by a simple co-occurrence script (lessons that share ≥3 key terms are "related"), rendered as a "See also" block at the bottom of each generated page. Small addition to `convert-to-markdown.js`, not a new system.

## 5. AI-powered Knowledge Assistant — RAG architecture

### What's built and live: retrieval-first, zero backend

```text
data/*.js
   │  (scripts/convert-to-markdown.js)
   ▼
docs-site/content/**/*.md
   │  (scripts/build-search-index.js — splits each page on H2 headings,
   │   strips Markdown syntax, keeps {title, section, page, url, text})
   ▼
docs-site/content/assets/embeddings/index.json   (271 chunks from 40 pages today)
   │  fetched client-side by assets/javascripts/assistant.js
   ▼
Browser: term-overlap scoring across the whole corpus, ranked results
   │  (optional, only if the user pastes their own key)
   ▼
Anthropic Messages API, called directly from the browser
(header: anthropic-dangerous-direct-browser-access), passed the
top-5 retrieved passages as context, asked to answer with citations
```

This is genuinely useful today — try it at `/assistant/` — and costs nothing to host, because there is no server: GitHub Pages serves static files, the "vector store" is a 200KB static JSON file, and "retrieval" is a scoring loop that runs in the visitor's own browser in milliseconds. Answer synthesis is opt-in and BYO-key, so the project itself never pays for or holds an API key.

**What this is not**: real embeddings. `index.json` is currently indexed by term-frequency-with-coverage-bonus (see `assistant.js`'s `score()` function), not by dense vector similarity — it's semantically weaker than embeddings for paraphrased questions ("what happens if I paid the wrong person" won't necessarily match a lesson titled "Payment Returns" the way an embedding model would catch), but strong for the keyword-heavy queries analysts actually type ("AC04", "mule account", "CoP no match").

### Production-grade version (roadmap, not built)

| Layer | Current (built) | Production upgrade |
|---|---|---|
| Chunking | H2-section split, plain text | Same approach, works fine at any scale |
| Embeddings | None (term-frequency) | `text-embedding-3-small` (OpenAI) or Voyage AI embeddings — both have generous free/cheap tiers; compute once per lesson chunk in CI, store as float arrays alongside the JSON |
| Vector store | Flat JSON array, scored client-side | For &lt;5,000 chunks: still a flat JSON file, cosine similarity computed client-side in a Web Worker (no infra change needed). Beyond that: a hosted vector DB (Supabase pgvector, Pinecone free tier, or Cloudflare Vectorize) behind a small serverless function |
| Retrieval | Client-side JS, term scoring | Client-side JS, cosine similarity against embeddings — same architecture, better relevance |
| Generation | Direct browser → Anthropic API, user's own key | A small serverless proxy (Cloudflare Worker or Netlify Function) holding a project-owned API key server-side, rate-limited per IP, so visitors never need their own key |
| Hosting cost | £0 | Cloudflare Workers free tier (100k requests/day) + Anthropic API usage (Haiku is cheap: a few hundred Q&As per £1) |

The reason this is designed as an incremental upgrade path rather than a rebuild: the chunk schema (`{title, section, page, url, text}`) doesn't change when embeddings are added — you're only adding an `embedding: [0.021, -0.14, ...]` field to each object and swapping the scoring function. Nothing about the page structure, the build step ordering, or the widget's DOM needs to change.

## 8. GitHub best practices

**Current state**: single-branch (`master`), direct commits, no PR workflow yet — appropriate for a solo portfolio project at this stage. Below is the recommended structure for when either collaboration starts or the project wants to demonstrate professional workflow discipline (relevant to the portfolio positioning in §11).

### Branch strategy

- `master` — always deployable; `docs-deploy.yml` triggers on every push here.
- `content/<block-id>` (e.g. `content/fps-f5`) — one branch per new block being drafted, merged via PR once the block passes `docs-validate.yml`.
- `fix/<short-description>` — bug fixes.

### Pull request workflow

1. Branch from `master`.
2. Make changes to `data/*.js` only (never hand-edit `docs-site/content/**/*.md` directly — it's generated).
3. Open PR — `docs-validate.yml` runs automatically: regenerates Markdown, fails if the committed generated content is stale, lints, strict-builds, checks internal links.
4. Self-review or peer-review against the checklist: does every new lesson have all required schema fields (§2)? Do MCQs have exactly one correct answer index? Are examples original (never copied from paid/collected source material)?
5. Squash-merge to `master` → deploy workflow runs automatically.

### Commit conventions

Follow [Conventional Commits](https://www.conventionalcommits.org/), matching the style already used in this repo's history (e.g. `Add FPS Block F4: Investigations (lessons 16-21)`):

```text
feat(fps): add Block F5 — Reconciliation & Architecture (lessons 22-25)
fix(app): correct hardcoded blockId in progress tracking
docs(architecture): document RAG upgrade path
ci(workflows): add markdown lint step
```

### Release strategy

Tag a release whenever a full block (or full track) completes:

```text
v0.5.0 — FPS F4 complete (21/40 FPS lessons)
v0.6.0 — FPS F5 complete, search feature shipped
v1.0.0 — All 40 FPS lessons + CPCM Blocks A-H complete
```

### Changelog

A `CHANGELOG.md` at the repo root, updated per release, one entry per block/feature:

```markdown
## [0.6.0] — 2026-07-30
### Added
- Global search across lessons, flashcards, quiz questions, glossary (legacy app)
- MkDocs Material documentation site with built-in search
- Retrieval-based Knowledge Assistant (`/assistant/`)
### Changed
- Corrected FPS course-map lesson-number gaps (F4/F6/F7/F8)
```

### Documentation standards

- Every new track/block gets one paragraph in the root `README.md`'s roadmap table before its first lesson is merged.
- `docs-site/README.md` documents the build/generate/serve commands for anyone else touching the docs site.
- This file (`ARCHITECTURE.md`) is the living design record — update it when a roadmap item above ships.

## 9. GitHub Actions

Two workflows are implemented in `.github/workflows/`:

### `docs-validate.yml` — runs on every PR and push

Regenerates Markdown from `data/*.js`, fails the build if the committed Markdown doesn't match (enforcing the single-source-of-truth rule from §1), lints Markdown style (non-blocking), strict-builds MkDocs (blocking — catches broken nav references and bad Markdown extension syntax), checks for broken internal links via `lychee`, and syntax-checks every legacy `data/*.js` file and `app.js`.

### `docs-deploy.yml` — runs on push to `master`

Regenerates Markdown, rebuilds the retrieval index, builds MkDocs, assembles a combined Pages output (docs site at root, legacy app at `/app/`), and deploys via `actions/deploy-pages`.

Both files are complete and committed in this repo at `.github/workflows/`. Search-index generation is folded into the deploy workflow rather than being a separate workflow, since it always needs to run immediately before the MkDocs build that ships it.

## 10. Migration plan — from scattered source docs to structured Markdown

This project's actual migration precedent (documented for reuse, since you mentioned 110+ lessons across Word/PDF/text sources): FPS Blocks F1–F4 were built by extracting a messy combined source file (`FPS_Full_Curriculum_Combined_fixed.md`, 13,626 lines, all 40 lessons), reading each lesson's raw content in full, then rewriting every fact and example in original wording into the fixed lesson schema (§2) — never copy-pasting the source's exact sentences, per your explicit instruction to keep the published site copyright-safe.

### Repeatable process for the remaining 19 FPS lessons + 35 CPCM lessons (and any future 110+-lesson source)

1. **Extract** — for a single source file, locate each lesson's line range (`grep -n "^# Lesson"` gives headers + line numbers, as used for F4); for scattered Word/PDF files, convert each to text first (`python-docx` for `.docx`, `pdfplumber` or the `pdf` skill for `.pdf`).
2. **Read in full** — no skimming; the rewriting step below is only trustworthy if every fact, code, and example in the source was actually seen.
3. **Rewrite into the schema** — map source content into `objectives` / `explanation` / `keyTerms` / `example` / `diagram` / `comparison` / `examTips` / `memoryTrick` / `keyPoints` / `mcqs` / `scenarios`, in original wording and with original worked examples throughout — never verbatim.
4. **Add metadata** — lesson number, tag, and (per §4's roadmap) topic tags.
5. **Generate summaries** — the `objectives` field doubles as the page summary/meta description; kept to one clear paragraph per lesson by convention.
6. **Generate tags** — currently block/lesson title; extending to topic-level tags (ISO codes, regulation names, system names mentioned) is a small addition to the lesson object, no pipeline change.
7. **Cross-links** — handled today via block index pages; the `related` field (§4 roadmap) is the next step for lesson-to-lesson linking.
8. **Glossary entries** — new terms surfaced during a block's writing get added to `data/glossary-extra.js` as `[term, definition, group]` tuples; the glossary page and legacy app's glossary view regenerate automatically.
9. **Navigation** — entirely automatic: adding a lesson to a block's `lessons` array is the only manual step; `convert-to-markdown.js` generates its page and updates the block index; `mkdocs.yml`'s `nav:` only needs a new line when a whole new *block* (not lesson) is added.

### Automation ideas (Python + AI) for a larger, messier source set

For a genuinely disorganized 110+-document source set (mixed Word/PDF/notes, inconsistent structure, possible duplicate content):

```python
# Rough pipeline shape, not a finished tool:
# 1. Inventory: walk the source folder, extract raw text from every file
#    (python-docx for .docx, pdfplumber for .pdf, plain read for .txt/.md)
# 2. Dedup: hash near-identical paragraphs (difflib.SequenceMatcher ratio > 0.9)
#    to flag likely duplicate source content before it's read twice
# 3. Segment: use heading detection (regex on "Lesson N", "Module N", font-size
#    metadata from docx, etc.) to split each file into candidate lesson units
# 4. Draft: for each candidate unit, an LLM call drafts a first-pass mapping
#    into the lesson schema (§2) — objectives, explanation, key terms —
#    explicitly prompted to paraphrase and invent fresh examples, never quote
# 5. Human review: every AI draft is read against the schema checklist (§8)
#    before being committed — this step is not skippable for a public site
# 6. Commit: append to the relevant data/<track>-blockN.js file
```

Step 4 is exactly the same "read fully, then rewrite originally" process used for F1–F4 in this repo, just proposing a first draft instead of a human writing it cold — the human review step (5) stays mandatory, both for copyright safety and factual accuracy.
